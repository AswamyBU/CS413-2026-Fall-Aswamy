# LAMBDA-studio Database Service — API v1

This document is the contract for the in-memory database service. It was
written before the routes were implemented, and the tests check the service
against it. A machine-readable description of the same contract is in
[`openapi.json`](openapi.json) (OpenAPI 3.1; its `components.schemas` are JSON
Schema 2020-12 and are used by the tests to validate every response body).

> **Data lifetime.** All records live in the memory of the service process.
> They survive browser reloads and new browser sessions while the process
> runs, and are **lost when the process stops**. There is no file, SQLite,
> cloud, or browser-storage persistence. List cursors are in memory too and
> also expire when the process stops.

The service only **stores** studio data. It never parses, type-checks,
interprets, or compiles LAMBDA source. Running tests is the studio's job: it
reads stored cases from this service and sends each one to the LAMBDA3
JSON-RPC service from Assign07.

## 1. Transport

| Item | Value |
| --- | --- |
| Base URL | `http://127.0.0.1:8009/api/v1` (default port; see README) |
| Style | REST: resource-oriented URLs, standard methods, JSON bodies |
| Request media type | `application/json` (UTF-8) for every request that has a body (`POST`, `PUT`). Otherwise `415`. |
| Response media type | `application/json; charset=utf-8` for every response with a body, including errors. `204` responses have no body. |
| Versioning | The major version is in the path (`/api/v1`). `GET /api/v1/health` reports `"version": "1.0"`. |
| Concurrency control | `ETag` on responses that return one record; `If-Match` required on every update and delete. |
| IDs | Opaque strings generated by the service (`prg_…`, `col_…`, `case_…`). Clients never invent IDs. |
| Time | UTC ISO 8601 with milliseconds and `Z`, e.g. `"2026-11-23T19:05:12.345Z"`. |

## 2. Route table

| Method and route | Request | Success | Headers |
| --- | --- | --- | --- |
| `GET /api/v1/health` | — | `200` `{"status":"ok","version":"1.0"}` | |
| `POST /api/v1/programs` | `ProgramInput` | `201` `{"program": Program}` | `ETag`, `Location` |
| `GET /api/v1/programs?limit&cursor` | query | `200` `{"items": [Program], "next_cursor": string\|null}` | |
| `GET /api/v1/programs/{id}` | — | `200` `{"program": Program}` | `ETag` |
| `PUT /api/v1/programs/{id}` | `ProgramInput` + `If-Match` | `200` `{"program": Program}` | `ETag` |
| `DELETE /api/v1/programs/{id}` | `If-Match` | `204` | |
| `POST /api/v1/collections` | `CollectionInput` | `201` `{"collection": Collection}` | `ETag`, `Location` |
| `GET /api/v1/collections?limit&cursor` | query | `200` `{"items": [Collection], "next_cursor": string\|null}` | |
| `GET /api/v1/collections/{id}` | — | `200` `{"collection": Collection}` | `ETag` |
| `PUT /api/v1/collections/{id}` | `CollectionInput` + `If-Match` | `200` `{"collection": Collection}` (metadata only; cases unchanged) | `ETag` |
| `DELETE /api/v1/collections/{id}` | `If-Match` | `204` (its cases are deleted with it) | |
| `POST /api/v1/collections/{id}/cases` | `CaseInput` + collection `If-Match` | `201` `{"collection": Collection}` (case appended) | `ETag` |
| `PUT /api/v1/collections/{id}/cases/{case_id}` | `CaseInput` + collection `If-Match` | `200` `{"collection": Collection}` (same ID and position) | `ETag` |
| `DELETE /api/v1/collections/{id}/cases/{case_id}` | collection `If-Match` | `200` `{"collection": Collection}` (others keep their order) | `ETag` |

Any other path returns `404 record_not_found`. A known path with another
method returns `405 method_not_allowed` with an `Allow` header.

## 3. Schemas

### 3.1 Request bodies

All request bodies are JSON objects. **Unknown fields are rejected** (`400`),
including server-managed fields (`id`, `created_at`, `updated_at`,
`revision`, `cases`).

```text
ProgramInput    = { "name": string, "source": string, "description"?: string }
CollectionInput = { "name": string, "description"?: string }
CaseInput       = { "name": string, "source": string, "expected": Expected,
                    "description"?: string }
Expected        = { "kind": "value", "value": string }
                | { "kind": "error", "category": "syntax" | "type" }
```

- `name`: required string. Leading/trailing whitespace is trimmed; the
  trimmed name is stored and returned. It must be nonempty after trimming
  and at most 100 characters.
- `source`: required string. Must contain a non-whitespace character and be
  at most 65,536 UTF-8 bytes. It is stored exactly as sent (not trimmed).
- `description`: optional string, at most 2,000 characters, default `""`.
  `PUT` is a full replacement of the editable fields, so omitting
  `description` in a `PUT` sets it to `""`.
- `expected`: exactly one of the tagged shapes. Unknown fields inside it are
  rejected. `value` is a nonempty string of at most 10,000 characters.

### 3.2 Response representations

```text
Program    = { "id": string, "name": string, "source": string,
               "description": string, "created_at": string,
               "updated_at": string, "revision": integer >= 1 }
Collection = { "id": string, "name": string, "description": string,
               "created_at": string, "updated_at": string,
               "revision": integer >= 1, "cases": [Case] }
Case       = { "id": string, "name": string, "source": string,
               "expected": Expected, "description": string }
Error      = { "error": { "code": string, "message": string, ...details } }
```

Every documented field is always present. List `items` are full
representations; collection list items include their ordered `cases`.

## 4. Revisions, ETags, and preconditions

- A new program or collection has `revision: 1`. Each successful update adds
  exactly 1. For a collection, adding, updating, or deleting a case is an
  update of the collection (one increment per request).
- A delete checks the revision but does not create a new revision.
- `ETag` is a strong entity tag holding the quoted decimal revision:
  `ETag: "3"`. Clients send the same value back: `If-Match: "3"`. Any other
  form (`*`, `W/"3"`, a list, an unquoted number) is `400 invalid_request`.
- Case routes use the **parent collection's** `ETag` and revision. A case
  has no revision of its own.
- `updated_at` changes on every successful update. `created_at` never changes.

**Order of checks** for `PUT`/`DELETE` (and `POST …/cases`). The first
failing check decides the response:

1. The route is malformed (e.g. an ID with the wrong format): `400`.
2. The record does not exist: `404`. This applies even when `If-Match` is
   missing or stale. A missing case inside an existing collection is also
   `404`.
3. `If-Match` is missing: `428 precondition_required`.
4. `If-Match` is malformed: `400 invalid_request`.
5. The body is not `application/json`: `415`. The body is malformed or
   invalid: `400`.
6. `If-Match` does not equal the current revision:
   `409 revision_conflict`, with `current_revision` in the body.
7. A name is a duplicate: `409 duplicate_name`. A capacity limit is
   reached: `409 capacity_limit`.

All of these checks and the write happen while holding one lock, so a
mutation is atomic. Either the whole change is visible or none of it is, and
a failed request leaves the record exactly as it was.

## 5. Uniqueness rules

Names are compared **after trimming**, case-sensitively:

- Program names are unique among programs.
- Collection names are unique among collections.
- Case names are unique among the cases of the **same** collection.

A program, a collection, and a case may share a name, and two collections
may each contain a case with the same name. Renaming a record to its own
current name is allowed.

## 6. Pagination

`GET /programs` and `GET /collections` accept only these query parameters:

| Parameter | Rule |
| --- | --- |
| `limit` | Integer 1–100 (digits only), default 50. |
| `cursor` | Opaque token from a previous `next_cursor`. |

Any other query parameter, or a repeated parameter, is `400`.

- **Order:** records are ordered by creation time. Ties are broken by a
  creation sequence number, so the order is deterministic.
- **Snapshots:** a request **without** a cursor takes a snapshot of the
  current records. Records are immutable values, so the snapshot holds the
  exact representations as they were at that moment. Each `next_cursor`
  names `(snapshot, offset)`. All later pages in that cursor chain come from
  the same snapshot, so they:
  - exclude records created afterwards;
  - still show the captured representation of records updated or deleted
    afterwards.
- `next_cursor` is `null` on the last page. An empty list has one page with
  `items: []`.
- **Cursor lifetime:** cursors are random tokens that index an in-memory
  table. A snapshot expires 10 minutes after it was last used. At most 256
  snapshots are kept; the least recently used is evicted beyond that. All
  cursors disappear when the process stops. An unknown or expired cursor is
  `400 invalid_request` with `"parameter": "cursor"`. The client should start
  again without a cursor.
- A cursor may be re-read: the same cursor returns the same page.

## 7. Limits

| Limit | Value | When exceeded |
| --- | --- | --- |
| Request body | 256 KiB | `413 payload_too_large` |
| `name` | 100 characters (after trim) | `400 invalid_request` |
| `source` | 65,536 UTF-8 bytes | `400 invalid_request` |
| `description` | 2,000 characters | `400 invalid_request` |
| `expected.value` | 10,000 characters | `400 invalid_request` |
| Page size (`limit`) | 1–100, default 50 | `400 invalid_request` |
| Programs | 1,000 | `409 capacity_limit` |
| Collections | 200 | `409 capacity_limit` |
| Cases per collection | 200 | `409 capacity_limit` |
| Live list snapshots | 256, 10-minute idle lifetime | oldest evicted; cursor becomes invalid |

Size and length errors include `field`, `limit`, and `actual` in the error
body. Capacity errors include `limit`.

## 8. Errors

Every error response has `Content-Type: application/json` and this body:

```json
{ "error": { "code": "revision_conflict",
             "message": "If-Match \"2\" does not match the current revision 3",
             "current_revision": 3 } }
```

| HTTP | `code` | When |
| --- | --- | --- |
| 400 | `invalid_request` | Malformed JSON, a body that is not an object, unknown/missing/wrong-typed/blank/oversized fields, a bad query parameter or cursor, a malformed ID or `If-Match`. Details: `field` or `parameter`, and `limit`/`actual` for size errors. |
| 404 | `record_not_found` | Unknown record ID, unknown case ID, or unknown route |
| 405 | `method_not_allowed` | Known route, unsupported method (`Allow` header lists the methods) |
| 409 | `duplicate_name` | Name already used in the same scope (`field: "name"`) |
| 409 | `revision_conflict` | Stale `If-Match` (`current_revision` included) |
| 409 | `capacity_limit` | Too many programs, collections, or cases (`limit` included) |
| 413 | `payload_too_large` | Request body over 256 KiB |
| 415 | `unsupported_media_type` | `POST`/`PUT` body not `application/json` |
| 428 | `precondition_required` | `PUT`/`DELETE` (or case `POST`) without `If-Match` on an existing record |
| 500 | `internal_error` | Unexpected failure. The message is generic; no traceback or path is ever sent. |

## 9. Examples

### Health

```http
GET /api/v1/health
→ 200  {"status": "ok", "version": "1.0"}
```

### Create a program

```http
POST /api/v1/programs
Content-Type: application/json

{"name": "factorial", "source": "let fact = fix f(n: sint): sint => if n <= 0 then 1 else n * f(n - 1) in fact(6) end", "description": "6!"}

→ 201  ETag: "1"   Location: /api/v1/programs/prg_3f9c2a1b7d4e8f60
{"program": {"id": "prg_3f9c2a1b7d4e8f60", "name": "factorial",
  "source": "let fact = fix f(n: sint): sint => ...", "description": "6!",
  "created_at": "2026-11-23T19:05:12.345Z", "updated_at": "2026-11-23T19:05:12.345Z",
  "revision": 1}}
```

### List (two pages)

```http
GET /api/v1/programs?limit=2
→ 200  {"items": [{...}, {...}], "next_cursor": "q0b4Yh2l1wE8kQ5bQm9fpA"}

GET /api/v1/programs?limit=2&cursor=q0b4Yh2l1wE8kQ5bQm9fpA
→ 200  {"items": [{...}], "next_cursor": null}
```

### Get

```http
GET /api/v1/programs/prg_3f9c2a1b7d4e8f60
→ 200  ETag: "1"   {"program": {..., "revision": 1}}
```

### Update

```http
PUT /api/v1/programs/prg_3f9c2a1b7d4e8f60
Content-Type: application/json
If-Match: "1"

{"name": "factorial", "source": "... fact(5) end", "description": "5!"}

→ 200  ETag: "2"   {"program": {..., "description": "5!", "revision": 2}}
```

### Stale revision conflict

```http
PUT /api/v1/programs/prg_3f9c2a1b7d4e8f60
If-Match: "1"
...
→ 409  {"error": {"code": "revision_conflict",
                  "message": "If-Match \"1\" does not match the current revision 2",
                  "current_revision": 2}}
```

### Delete

```http
DELETE /api/v1/programs/prg_3f9c2a1b7d4e8f60
If-Match: "2"
→ 204  (no body)
```

### Invalid parameter

```http
GET /api/v1/programs?limit=500
→ 400  {"error": {"code": "invalid_request",
                  "message": "limit must be an integer from 1 to 100",
                  "parameter": "limit"}}

POST /api/v1/programs   {"name": "  ", "source": "1"}
→ 400  {"error": {"code": "invalid_request", "message": "name must not be blank",
                  "field": "name"}}
```

### Collections and cases

```http
POST /api/v1/collections   {"name": "basics"}
→ 201  ETag: "1"  {"collection": {"id": "col_…", "name": "basics", "description": "",
                    "created_at": "…", "updated_at": "…", "revision": 1, "cases": []}}

POST /api/v1/collections/col_…/cases     If-Match: "1"
{"name": "six factorial", "source": "...", "expected": {"kind": "value", "value": "720"}}
→ 201  ETag: "2"  {"collection": {..., "revision": 2,
          "cases": [{"id": "case_…", "name": "six factorial", "source": "...",
                     "expected": {"kind": "value", "value": "720"}, "description": ""}]}}

PUT /api/v1/collections/col_…/cases/case_…   If-Match: "2"
{"name": "bad syntax", "source": "1 +", "expected": {"kind": "error", "category": "syntax"}}
→ 200  ETag: "3"  {"collection": {..., "revision": 3, "cases": [ ...same id, same position... ]}}

DELETE /api/v1/collections/col_…/cases/case_…   If-Match: "3"
→ 200  ETag: "4"  {"collection": {..., "revision": 4, "cases": []}}
```

## 10. Expected outcomes and how the studio matches them

The database stores `expected` as data and never checks whether it is
correct. When the studio runs a collection, it sends each case's stored
`source` to LAMBDA3's `lambda.interpret` method and compares the outcome:

| `expected` | Passes when |
| --- | --- |
| `{"kind":"value","value":V}` | `lambda.interpret` succeeds and `result.value` is exactly `V` |
| `{"kind":"error","category":"syntax"}` | the JSON-RPC error code is `-32010` (LAMBDA syntax error) |
| `{"kind":"error","category":"type"}` | the JSON-RPC error code is `-32011` (LAMBDA type error) |

Everything else counts as a fail and never as an expected error: a timeout
(`-32012`), a runtime error, a transport failure, or any other server
error.

Cases hold **source snapshots**. Editing or deleting a program never changes
an existing case.
