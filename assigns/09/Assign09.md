# Assignment #9

## Building an In-Memory Database Service for LAMBDA-studio

## Due date

Monday, the 30th of November

## Attention

Keep everything you submit in `assigns/09/MySolution/`.

## Objective

Build a small in-memory database service that gives LAMBDA-studio a place to
keep named LAMBDA programs and reusable test collections while the service is
running. The project is the final integration project for the LAMBDA-studio
and applies service-oriented programming: define a client-facing service
contract, implement the service independently of its clients, and integrate
the browser studio through that contract.

The service stores and retrieves studio data. It does not parse, type-check,
interpret, or compile LAMBDA programs. Those operations belong to the existing
LAMBDA3 service from Assign07 (and the stream service from Assign08 where
applicable). A browser client should be able to create and edit a program,
save it, reload it in a later browser session while the service is still
running, and organize test cases into named collections.

## Starting point and scope

Use Python 3.12 or later and an instructor-approved HTTP framework. The
service is local and single-user. Keep all records in process memory using
ordinary data structures; do not use SQLite, a cloud database, files, browser
storage, or another persistence layer for the required database. Data survives
client reloads but is lost when the service process stops. This limitation
must be visible in the documentation and the studio interface.

Use a REST API over HTTP with resource-oriented URLs and standard HTTP
methods. Define a versioned, documented contract before implementing routes.
Successful methods return JSON representations, never Python objects. The
service must not execute user-supplied LAMBDA source. It may be tested
independently of the browser, but the final submission must include a working
studio integration or a small client page that demonstrates the integration.

Required stored entities:

1. **Program** — an opaque ID, nonempty name, LAMBDA source text, optional
   description, creation time, update time, and monotonically increasing
   revision number.
2. **Test collection** — an opaque ID, nonempty name, optional description,
   ordered test cases, creation time, update time, and revision number.
3. **Test case** — an opaque ID within a collection, name, LAMBDA source text,
   expected outcome, and optional description. Expected outcomes are either a
   successful formatted value or an expected syntax/type-check error category.

Test cases contain source snapshots. They do not depend on a mutable program
record, so editing or deleting a program cannot silently change an existing
test. Test execution is outside the database service: LAMBDA-studio obtains
the stored cases and invokes the LAMBDA3 service for each case.

## Required service contract

Implement these resource-oriented routes. IDs are opaque strings generated by
the service; clients must not invent IDs. Returned records include all
documented fields. Timestamps use UTC ISO 8601 strings. Successful reads and
writes return JSON; successful deletes may return `204 No Content`.

| Method and route | Request | Response / behavior |
| --- | --- | --- |
| `GET /api/v1/health` | None | `200` with `{ "status": "ok", "version": "1.0" }` |
| `POST /api/v1/programs` | `{ "name": "...", "source": "...", "description": "..." }` | `201` with `{ "program": { ... } }`; description may be omitted or empty |
| `GET /api/v1/programs?limit=50&cursor=...` | Query parameters | `200` with `{ "items": [ ... ], "next_cursor": null }`; stable ordering and bounded page size |
| `GET /api/v1/programs/{id}` | None | `200` with `{ "program": { ... } }` and an `ETag` for its revision |
| `PUT /api/v1/programs/{id}` | `{ "name": "...", "source": "...", "description": "..." }` and `If-Match` | `200` with `{ "program": { ... } }` and updated `ETag`; update only when revision matches |
| `DELETE /api/v1/programs/{id}` | `If-Match` | `204`; delete only when revision matches |
| `POST /api/v1/collections` | `{ "name": "...", "description": "..." }` | `201` with `{ "collection": { ... } }` |
| `GET /api/v1/collections?limit=50&cursor=...` | Query parameters | `200` with `{ "items": [ ... ], "next_cursor": null }` |
| `GET /api/v1/collections/{id}` | None | `200` with `{ "collection": { ... } }`, including ordered cases, and an `ETag` for its revision |
| `PUT /api/v1/collections/{id}` | `{ "name": "...", "description": "..." }` and `If-Match` | `200` with `{ "collection": { ... } }` and updated `ETag`; updates metadata only, leaving cases and their order unchanged |
| `DELETE /api/v1/collections/{id}` | `If-Match` | `204`; delete only when revision matches |
| `POST /api/v1/collections/{id}/cases` | `{ "name": "...", "source": "...", "expected": { ... }, "description": "..." }` and collection `If-Match` | `201` with `{ "collection": { ... } }` and updated `ETag`; appends one case and increments collection revision |
| `PUT /api/v1/collections/{id}/cases/{case_id}` | `{ "name": "...", "source": "...", "expected": { ... }, "description": "..." }` and collection `If-Match` | `200` with `{ "collection": { ... } }` and updated `ETag`; updates the case in place, preserving its ID and order, and increments collection revision |
| `DELETE /api/v1/collections/{id}/cases/{case_id}` | Collection `If-Match` | `200` with `{ "collection": { ... } }`; removes the case, preserves remaining order, and increments collection revision |

Program representations contain `id` (opaque string), `name` (string), `source`
(string), `description` (string, possibly empty), `created_at` and `updated_at`
(UTC ISO 8601 strings), and `revision` (positive integer). Collection
representations contain `id`, `name`, `description`, `created_at`,
`updated_at`, `revision`, and `cases` (an ordered array of case
representations). A case representation contains `id` (opaque string unique
within its collection), `name`, `source`, `expected`, and `description`.
Create and update request bodies omit server-managed fields (`id`, timestamps,
and revisions); clients must not send unknown fields. Names and source are
required nonempty strings. Descriptions are optional strings and default to
empty. In list responses, each `items` entry is a full program or collection
representation as applicable; collection list entries include their ordered
cases.

New records start at revision `1`. Each successful update increments the
revision by exactly one; delete checks the current revision but does not
produce a new record revision. Use a strong entity tag formatted as a quoted
decimal revision, such as `ETag: "3"`; send that exact value in `If-Match`,
such as `If-Match: "3"`. Case mutations use the parent collection's ETag and
revision. A missing record returns `404` even if its `If-Match` value is
missing or stale; for an existing record, a missing `If-Match` returns `428`.

Names are unique among programs, among collections, and among cases within
the same collection, after trimming leading and trailing whitespace. The
trimmed name is stored and returned. Names in different entity kinds or
different collections may be equal.

Define `expected` as one of these tagged JSON shapes:

```json
{ "kind": "value", "value": "720" }
{ "kind": "error", "category": "syntax" }
{ "kind": "error", "category": "type" }
```

The value is the formatted value returned by the LAMBDA3 service. The
database treats it as data; it does not decide whether the expected result is
correct.

For `kind: "error"`, `category: "syntax"` matches the LAMBDA3 syntax-error
category and `category: "type"` matches its type-checking-error category. A
timeout, transport failure, or unexpected server error is not a match for
either expected error. A value expectation matches only when the execution
succeeds and its formatted value is exactly equal to `value`.

### Contract rules

- Validate JSON content types, route parameters, request fields, and documented
  size limits. Use `400` for malformed JSON or invalid parameters, `404` for
  missing records or routes, `405` for a known route with an unsupported
  method, `409` for duplicate names, revision conflicts, or capacity limits,
  `413` for oversized HTTP request bodies, `415` for unsupported media types,
  and `500` for unexpected server failures. Return a consistent JSON error
  body such as
  `{ "error": { "code": "revision_conflict", "message": "...", "current_revision": 3 } }`.
  Use stable machine-readable codes including `invalid_request`,
  `record_not_found`, `duplicate_name`, `revision_conflict`,
  `capacity_limit`, and `internal_error`. Use `invalid_request` for invalid
  fields, parameters, or malformed JSON; `record_not_found` for a missing
  record or route; `duplicate_name` for a uniqueness violation;
  `revision_conflict` for a stale `If-Match`; `capacity_limit` for an entity
  or collection capacity limit; and `internal_error` for unexpected failures.
  Include the current revision in a revision-conflict body when the record
  exists. Do not leak internal failure details. Error responses use
  `Content-Type: application/json` and the documented error envelope.
- Reject unknown request fields. Names are unique according to the scope and
  trimming rules above; reject blank names. Source text must be a nonempty
  string. `expected` must match exactly one of the tagged shapes above; reject
  unknown fields within it as well.
- Set limits for source size, description length, page size, collection case
  count, and total records. Return a useful parameter error when a limit is
  exceeded. Document the chosen limits.
- `list` methods use deterministic ordering and opaque cursors. The first
  page establishes a snapshot; all later pages in its cursor chain return the
  same record representations in the same order, even if records are added,
  updated, or deleted meanwhile. The snapshot excludes later additions and
  retains the captured representation of later-updated or deleted records.
  Cursors expire when the service process stops. Document the snapshot-token
  strategy and its in-memory lifetime.
- Updates and deletes require the current revision in `If-Match`; responses
  include the current revision in `ETag`. On success, each mutation
  increments the revision exactly once. A stale revision returns a conflict
  error and leaves the record unchanged. Mutating an embedded test case also
  increments its collection revision.
- A mutation is atomic: callers observe either its complete effect or no
  effect. Protect shared state appropriately for the chosen server model.
- Deleting a collection removes its cases. Deleting a program has no effect on
  test case snapshots.
- Use standard HTTP status codes consistently and document the error body
  shape. Set appropriate `Content-Type` headers and use `ETag`/`If-Match` for
  conditional mutations. A missing precondition header returns `428`.

## LAMBDA-studio integration

Add a storage adapter in the studio client so UI code does not spread route
and HTTP details throughout the interface. The studio must support these
user flows:

1. List saved programs, create one, open one, edit it, and save changes.
2. Show and handle a stale-revision conflict without overwriting the newer
   saved version silently; allow the user to reload the server copy.
3. Create a named test collection, add/edit/delete test cases, and reload the
   collection from the service.
4. Send each saved test case to the LAMBDA3 service when the user runs the
   collection, compare its outcome with the stored expectation, and show a
   per-case pass/fail summary. One failure must not stop the remaining cases.
5. Clearly identify unsaved edits and explain that database contents are
   cleared when the service stops.

The studio may use the existing interface from Assign03 and the services from
Assign07/Assign08, or provide an equivalent small demonstration client if the
earlier interface is not directly reusable. Do not replace LAMBDA3 with a
mock when demonstrating successful test execution. For database-only API
tests, use deterministic service data created through the public interface.

## Tasks

### 1. Specify the service

Before implementing the routes, write `API.md` containing:

- The transport contract and route table with complete request and response
  schemas.
- Request and response examples for create/list/get/update/delete, a stale
  revision conflict, and an invalid parameter.
- HTTP status codes and stable API error codes.
- Record fields, expected-outcome variants, uniqueness rules, limits,
  pagination semantics, revision behavior, and process-lifetime data behavior.
- OpenAPI documentation for the REST routes and payloads, or JSON Schema for
  all request and response bodies.

### 2. Implement the database service

Separate HTTP routes, request validation, business rules, and storage. Keep
the storage layer replaceable behind a small interface, but implement the
required in-memory backend. Do not place all logic in route handlers. Keep
operations small and return explicit record representations.

### 3. Implement the studio adapter and workflows

Keep REST details in a client adapter. Handle network errors, HTTP/API errors,
validation feedback, unsaved edits, and stale revisions in the interface.
During a collection run, associate each result with the source snapshot and
case ID that produced it so an edit made during execution cannot mislabel the
result.

### 4. Test and document

Automated tests must exercise the API through the HTTP test client and cover:

1. Health, content types, and malformed/invalid requests.
2. Create, list, get, update, and delete for programs and collections.
3. Add, update, delete, and ordered retrieval of test cases.
4. Validation of missing, wrongly typed, blank, oversized, and unknown fields.
5. Duplicate-name behavior, unknown record IDs, and page/cursor boundaries.
6. Revision increments, stale-update/delete conflicts, and no partial mutation
   after failed operations.
7. Atomic behavior under concurrent update attempts, with exactly one update
   succeeding when both use the same revision.
8. Deleting a collection and verifying its cases are gone; deleting a program
   and verifying test case snapshots remain unchanged.
9. A studio-level integration demonstration that saves and reloads a program,
   creates/runs a test collection through the LAMBDA3 service, and reports an
   expected success and expected error case.

Write `README.md` with versions, setup, test/start commands, endpoint URL,
limits, and examples. Write `TESTING.md` mapping behaviors to test names and
recording observed results. Include an architecture diagram showing the
studio, storage adapter, REST API, in-memory store, and LAMBDA3 service. Write
`AI-TRANSCRIPT.md` with AI tools and significant assistance,
plus your review process, or state explicitly that no AI was used.
